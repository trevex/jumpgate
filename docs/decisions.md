# Key decisions

The load-bearing architecture decisions and why we made them. Update this page when a
decision changes or a new one is made.

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Backend split | Go control plane, Go and Rust data plane | Go wins the k8s operator ecosystem, ReBAC engines, enterprise SSO, and team velocity; Rust wins proxy performance and safety and is uniquely strong for the RDP worker (IronRDP). Each worker is written in the best language for its protocol. |
| Data-plane shape | Two-tier: thin gateway plus per-protocol workers | Independent per-protocol scaling and per-protocol language freedom behind one protocol-agnostic gateway. |
| Proxy posture | Agentless L7 proxy for SSH, Postgres, and RDP; dial-out agent for Kubernetes | No software on SSH/Postgres/RDP targets, the lowest adoption friction. Kubernetes cannot be reached the same way without inbound access to a customer cluster, so a lightweight agent runs inside the cluster and dials out over mesh mTLS — jumpgate opens no inbound port and holds no long-lived cluster credential. |
| Kubernetes tunnel | Agent dials the broker; roles reverse to make the agent the HTTP/2 server | The agent (in the target cluster) opens the connection outbound, then serves HTTP/2 on it while the broker becomes the client. The broker holds one tunnel per asset and sets impersonation headers from the verified token; the gateway routes by the token's `broker_id` with no asset map (a stale broker returns a retriable 503). Reuses plain HTTP/2 rather than a multiplexer library. |
| Kubernetes identity | Impersonate the user's email plus token-carried `k8s:group` set | Email is the conventional OIDC subject cluster RBAC binds against, not an internal UUID. Groups are enumerated from concrete `k8s:group:<name>` capabilities, so wildcards grant nothing and a jumpgate admin is not cluster-admin. What a group can do is delegated to the cluster's own RBAC. |
| Data-plane trust | Control plane brokers, workers enforce | Security-critical state stays centralized in Go; workers are stateless and hold secrets only for a live session; revocation is immediate. |
| Access model | Custom Role plus RoleBinding (relationship-based, resolved in-engine) | Enterprise-grade custom roles; the relationship graph handles nested groups and folder inheritance, and the control plane resolves roles to a fixed capability vocabulary. See the Authz-engine row for the backend. |
| Role model | Explicit ReBAC-light userset-rewrite (fixed types, user-definable roles plus rewrite rules); `HoldsRole` recursive CTE; folder cascade of standing access is explicit (a declared `parent` rule), no implicit cascade | Flexible role composition and folder cascade without OpenFGA's arbitrary-type generality; easy to reason about (`ExplainRole` shows the chain). |
| Discoverability | Permission-gated (Active ∪ Requestable), 404 not 403 | Least privilege and need-to-know; asset existence is never leaked to unauthorized users. Requestable is rule-based (a RequestPolicy the caller is eligible for), not a per-subject binding. |
| Postgres escalation | Inline per-statement approval plus time-boxed tiered step-up (design intent; not yet built) | Access-when-you-need-it done robustly on a structured protocol, DB-enforced via `SET ROLE`. Today Postgres uses pre-session grants like SSH; inline per-statement enforcement is deferred. |
| SSH escalation | Pre-session only | Parsing commands from an interactive TTY is not a robust enforcement boundary; keep it honest. |
| Session token | PASETO v4.public (ed25519) | Simpler and more misuse-resistant than JWT. |
| Identity (MVP) | Local accounts first | Fastest to iterate; OIDC/SAML/SCIM is a later sub-project. |
| User deactivation | `users.deactivated_at`; enforced at Login (no new token), the auth interceptor (any authenticated RPC → `Unauthenticated`), and every authz closure (`deactivated_at IS NULL` filter) | Immediate, revocable off-switch for a principal without deleting bindings or history. A deactivated user holds nothing and counts for nothing in anyone's resolution; their active grants are revoked and dependent sessions torn down. See [security.md](security.md#account-deactivation). |
| Authz engine | `Authorizer` seam plus a roll-our-own Postgres/recursive-CTE backend | Our model (nested groups, explicit role-rewrite folder cascade, Active/Requestable tiers) maps cleanly to recursive SQL CTEs and avoids OpenFGA's heavy in-process footprint. OpenFGA (embedded or sidecar) remains a drop-in behind the seam. |
| Capability storage | Decomposed into `role_capabilities(scope, action, qualifier)` rows, indexed; matched by a three-column SQL predicate proven equivalent to the Go `CapMatch` glob | An indexed keyed lookup instead of scanning a jsonb array, with the reference glob semantics kept in one Go function and pinned equal to the SQL path by a test. |
| Data layer | sqlc plus pgx/v5 plus goose (embedded migrations) | Type-safe SQL without ORM magic; migrations embedded in the binary; tests run against an ephemeral Postgres (initdb/pg_ctl), no Docker. |
| API layer | ConnectRPC (connect-go) over buf; opaque DB-backed bearer tokens | One proto contract for browser, CLI, and Go/Rust workers, no Envoy; protovalidate for validation; `CodeNotFound` hides non-visible resources; tokens are revocable server-side (not JWT). |
| CLI language | Go (cobra) | Shares the API client; clean static cross-compiles. |
| Frontend | React plus Vite SPA embedded in the backend binary | Matches the Teleport/hoop pattern; the largest ecosystem for data-heavy admin UIs. Built behind the `embedui` tag, so Go builds without a frontend toolchain. |
| Dev environment | Nix flake devshell plus direnv | One pinned, reproducible toolchain across contributors and CI. |
| Audit integrity | Hash-chained append-only log | Tamper-evident; a standard, auditor-accepted mechanism. |
| Request policy (requestability plus approval) | One `request_policies` row per (role, scope): its existence makes the role requestable there. Rule-based eligibility — requester = holders of `requester_role` on the scope ∪ explicit `requester` subjects; approver = holders of `approver_role` ∪ explicit `approver` subjects; role-level default plus per-scope override, most-specific wins; no policy means not requestable. `role_bindings` are standing-only. | Unifies who may request and who approves in one rule that composes with the role-rewrite graph (`HoldsRole`) instead of a subject-scoped binding; the gate travels with the role; folder and asset are distinct scope flows; no org/manager graph dependency. |
| Service layout | Focused ConnectRPC services: IdentityService, CatalogService, AccessService, AccessRequestService, plus VaultService, EnrollmentService, SessionService, RecordingService, GatewayService, and the mesh Dataplane contract | Clean boundaries: how access is defined (static, admin — AccessService) versus how it is obtained (dynamic, user and approver — AccessRequestService); catalog no longer conflates the resource tree with the whole RBAC model. |
| Secrets at rest | Envelope encryption: a fresh random per-secret 256-bit DEK encrypts the plaintext (AES-256-GCM); the DEK is wrapped by a master KEK (`VAULT_MASTER_KEY`, base64 32 bytes). Sealed bytes never leave the DB/API; `Open` is fail-closed. Master key is env now, KMS-pluggable (only the DEK-wrap step changes, so master-key rotation re-wraps DEKs, not ciphertexts). | Standard KMS-shaped envelope pattern: one small master key to protect, per-secret DEKs limit blast radius, and the KMS seam is a drop-in without re-encrypting data. Chose AES-256-GCM (stdlib, authenticated) over NaCl secretbox to keep the wrap/unwrap seam KMS-shaped. Tradeoff: losing the master key loses all sealed secrets (documented). |
| SSH cert principals | Capability-driven, Teleport-style: OS logins are `ssh:login:<account>` capabilities; the broker mints an SSH cert whose `ValidPrincipals` are the host-scoped `<login>@<asset>` forms of the asset's configured logins intersected with the user's held `ssh:login:*` (standing or active grant), reusing the glob-aware `Check`. Empty means refused; the CA also refuses a principal-less cert. | No static host logins and no per-host login config duplicating the authz graph — the account a user lands as is a strict function of their entitlements, and a JIT grant of a login role naturally scopes it in time. Host-scoping binds a login to a specific asset (enforced by the target's `AuthorizedPrincipalsFile`). Reuses the existing capability graph rather than a parallel mechanism. |
| Postgres credentials | Per-role logins with two kinds: `mtls` mints a short-lived X.509 client cert (CN = the DB role) from the X.509 client CA, and `password` returns the sealed stored password. Both gated by `db:login:<role>`. The pg-proxy worker is Go (on `jackc/pgx`), separate from the Rust ssh-proxy. | Reuses the same broker-mints-short-lived-credential model as SSH, on a structured protocol; certificate auth avoids a stored secret entirely. Go on pgx gets a mature pgwire stack; the two-tier gateway makes a per-protocol language choice free. |
| RDP access | Clientless browser sessions only — no local client, no CLI proxy. `CreateRDPSession` mints a cookie-authenticated ticket over a `GET /rdp` WebSocket, mirroring the browser SSH terminal; the rdp-proxy worker (Rust, IronRDP) performs the handshake and injects the sealed password, and a `jumpgate-rdp` WASM module renders the graphics stream in the browser. Logins are password-only, gated by `rdp:login:<login>`. | IronRDP is the mature Rust RDP stack, so the worker follows the same per-protocol-language pattern as ssh-proxy/pg-proxy. A clientless browser session avoids a local RDP client entirely and reuses the browser-terminal ticket/WebSocket path instead of a bespoke mechanism. |
| Per-kind asset config | Strongly-typed `assets.kind` (`ssh` / `postgres` / `k8s` / `rdp`) plus a per-kind config table: `ssh_asset_config` + `ssh_asset_login`, `postgres_asset_config` + `postgres_asset_login`, `rdp_asset_config` + `rdp_asset_login`, and no config table for `k8s` (the agent enrolls). `assets` stays the generic protocol-agnostic authz anchor. | A generic key/value credentials bag was rejected for a fixed, known asset set: typed tables give real columns and FK/CHECK constraints (a login's secret must belong to the same asset), at the cost of a migration per new kind — acceptable when kinds are few and deliberate. |
| JIT grant model | An approved (or self-service, `required_approvals=0`) request mints a time-boxed `access_grants` row (role for a user at an asset scope, with `expires_at`); the authorizer's held-closure base is `role_bindings ∪ active access_grants`, so a grant flows through the role-rewrite graph exactly like a standing binding and stops the instant it expires or is revoked. Grants are not governance: the requester/approver predicates resolve standing-only (`HoldsRoleStanding`). Revocation is expiry (30s reaper), manual `RevokeGrant` (a holder of `access:grant:revoke`, the subject, or a standing approver), or deactivation. Every revoke or expiry audits and tears down dependent live sessions. Duration is clamped to `min(requested, policy.max_duration, MaxGrantTTL=8h)`, snapshotted at request time. | One primitive for every time-boxed elevation (SSH grant, future Postgres step-up); grants join authz without mutating admin config; grants are not governance, which prevents self-escalation loops; symmetric approve/revoke authority; expiry is correct even without the reaper (the `expires_at > now()` filter), so the reaper is only an audit-and-teardown job. |

## Notable non-choices (deferred by design)

- MySQL/Mongo and HTTP/API proxying — later sub-projects; the two-tier data plane is
  designed so each is an additive worker, like RDP.
- Inline Postgres per-statement step-up and inline DLP / command blocking — deferred
  until the core is proven.
- AI-agent / MCP governance — a differentiation bet deferred until the core is proven.
- HA / multi-region — out of MVP scope.
