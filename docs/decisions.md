# Key decisions

The load-bearing architecture decisions and why we made them. Update this page
when a decision changes or a new one is made.

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Backend split | Go control plane + Rust data plane | Go wins the k8s operator ecosystem, ReBAC engines, enterprise SSO, and team velocity; Rust wins proxy performance/safety and is uniquely strong for future RDP (IronRDP). |
| Data-plane shape | Two-tier: thin gateway + per-protocol workers | Independent per-protocol scaling and per-protocol *language* freedom (a future worker can be Go) behind one protocol-agnostic gateway. |
| Proxy posture | Agentless L7 gateway | Lowest adoption friction; best fit for the JIT / data-protection story. No software on targets. |
| Data-plane trust | Control plane brokers, workers enforce | Security-critical state stays centralized in Go; workers are stateless and hold secrets only for a live session; revocation is immediate. |
| Access model | Custom Role + RoleBinding (relationship-based, resolved in-engine) | Enterprise-grade custom roles; the relationship graph handles nested groups + folder inheritance, the control plane resolves roles → a fixed capability vocabulary. See the Authz-engine row for the backend. |
| Role model | explicit ReBAC-light userset-rewrite (fixed types, user-definable roles + rewrite rules); HoldsRole recursive CTE; folder cascade of standing access is explicit (a declared `parent` rule), no implicit cascade | Flexible role composition + folder cascade without OpenFGA's arbitrary-type generality; easy to reason about (ExplainRole shows the chain). |
| Discoverability | Permission-gated (Active ∪ Requestable) + 404-not-403 | Least privilege / need-to-know; asset existence is never leaked to unauthorized users. Requestable is now rule-based (a RequestPolicy the caller is eligible for), not a per-subject binding. |
| Catalog visibility | Server-computed via the Authorizer; CodeNotFound for invisible assets | Discovery is permission-gated; asset existence never leaks to unauthorized users. |
| Postgres escalation | Inline per-statement approval + time-boxed tiered step-up | "Access when you need it" done robustly on a structured protocol; DB-enforced via `SET ROLE` (defense in depth). |
| SSH escalation | Pre-session only | Parsing commands from an interactive TTY is not a robust enforcement boundary; keep it honest. |
| Session token | PASETO v4.public (ed25519) | Simpler and more misuse-resistant than JWT. |
| Identity (MVP) | Local accounts first | Fastest to iterate; OIDC/SAML/SCIM is a later sub-project. |
| User deactivation | `users.deactivated_at`; enforced at **Login** (no new token), the auth **interceptor** (any authenticated RPC → `Unauthenticated`), **and** every authz closure (`deactivated_at IS NULL` filter) | Immediate, revocable off-switch for a principal without deleting bindings/history. A deactivated user holds nothing and counts for nothing in anyone's resolution; their active grants are revoked and dependent sessions torn down. See [security.md](security.md#account-deactivation). |
| Authz engine | `Authorizer` seam + roll-our-own Postgres/recursive-CTE backend | Our model (nested groups, explicit role-rewrite folder cascade, Active/Requestable tiers) maps cleanly to recursive SQL CTEs; avoids OpenFGA's heavy in-process footprint (separate store, many deps). OpenFGA (embedded or sidecar) remains a drop-in behind the seam. |
| Data layer | sqlc + pgx/v5 + goose (embedded migrations) | Type-safe SQL without ORM magic; migrations embedded in the binary; tests run against an ephemeral Postgres (initdb/pg_ctl), no Docker. |
| API layer | ConnectRPC (connect-go) over buf; opaque DB-backed bearer tokens | One proto contract for browser + CLI + future Rust gRPC workers, no Envoy; protovalidate for validation; CodeNotFound hides non-visible resources; tokens are revocable server-side (not JWT). |
| CLI language | Go (cobra) | Shares the API client; clean static cross-compiles. |
| Frontend | React + Vite SPA embedded in the backend binary | Matches the Teleport/hoop pattern; largest ecosystem for data-heavy admin UIs. |
| Dev environment | Nix flake devshell + direnv | One pinned, reproducible toolchain across contributors and CI. |
| Audit integrity | Hash-chained append-only log | Tamper-evident; standard, auditor-accepted mechanism. |
| Request policy (requestability + approval) | One `request_policies` row per (role, scope): its **existence ⇒ the role is requestable** there. Rule-based eligibility — requester = holders of `requester_role` on the scope ∪ explicit `requester` subjects (NOT per-subject `requestable` bindings, which are removed); approver = holders of `approver_role` ∪ explicit `approver` subjects; role-level default + per-scope override, most-specific wins; no policy ⇒ not requestable. `role_bindings` are **standing-only**. | Unifies "who may request" and "who approves" in one rule that composes with the role-rewrite graph (`HoldsRole`) instead of a subject-scoped binding; the gate travels with the role; folder vs asset are distinct scope flows; no org/manager graph dependency. |
| Service layout | Focused ConnectRPC services: **IdentityService** (users/groups/memberships/lifecycle), **CatalogService** (folders/assets + user-facing discovery), **AccessService** (all admin authz config: roles, role_grants, role_bindings, request_policies + subjects, ExplainRole), **AccessRequestService** (JIT runtime: RequestAccess/Approve/Deny/Cancel/Revoke + grants + reaper), plus VaultService, SessionService, RecordingService, GatewayService, and the mesh Dataplane contract | Clean boundaries: *how access is defined* (static, admin — AccessService) vs *how it is obtained* (dynamic, user + approver — AccessRequestService); catalog no longer conflates the resource tree with the whole RBAC model. |
| Secrets at rest | **Envelope encryption**: a fresh random per-secret **256-bit DEK** encrypts the plaintext (AES-256-GCM); the DEK is **wrapped** by a master **KEK** (`VAULT_MASTER_KEY`, base64 32 bytes). Sealed bytes never leave the DB/API; `Open` is fail-closed. Master key is **env now, KMS-pluggable** (only the DEK-wrap step changes → master-key rotation re-wraps DEKs, not ciphertexts). | Standard KMS-shaped envelope pattern: one small master key to protect, per-secret DEKs limit blast radius, and the KMS seam is a drop-in without re-encrypting data. Chose AES-256-GCM (stdlib, authenticated) over NaCl secretbox to keep the wrap/unwrap seam KMS-shaped. **Tradeoff:** losing the master key loses all sealed secrets (documented). |
| SSH cert principals | **Capability-driven, Teleport-style**: OS logins are `ssh:login:<account>` capabilities; the broker mints an SSH cert whose `ValidPrincipals` are the host-scoped `<login>@<asset>` forms of the asset's configured logins **∩** the user's held `ssh:login:*` (standing **or** active grant), reusing the glob-aware `Check`. Empty → refused; the CA also refuses a principal-less cert. | No static host logins / no per-host login config duplicating the authz graph — the account you land as is a strict function of your entitlements, and a JIT grant of a login role naturally scopes it in time. Host-scoping binds a login to a specific asset (enforced by the target's `AuthorizedPrincipalsFile`). Reuses the existing capability graph rather than a parallel mechanism. |
| Per-kind asset config | **Strongly-typed** `assets.kind` (`ssh`/`postgres`/`k8s`) + a **per-kind config table** (`ssh_asset_config` + per-login `ssh_asset_login`; Postgres/k8s configs planned); `assets` stays the generic protocol-agnostic authz anchor. | A generic `asset_credentials` key/value bag was **rejected** for a **fixed, known** asset set: typed tables give real columns and FK/CHECK constraints (e.g. a login's secret must belong to the same asset), and clarity, at the cost of a migration per new kind — acceptable when kinds are few and deliberate. |
| JIT grant model | An approved (or self-service, `required_approvals=0`) request mints a **time-boxed `access_grants` row** (role for a user at an asset scope, with `expires_at`); the authorizer's held-closure base is **`role_bindings` ∪ active `access_grants`**, so a grant flows through the role-rewrite graph exactly like a standing binding and stops the instant it expires/is revoked. **Grants≠governance:** the requester/approver predicates resolve **standing-only** (`HoldsRoleStanding`), so a JIT-granted role never lets you request or approve further. Revocation = **expiry** (background reaper, `ReaperInterval` 30s) **· manual `RevokeGrant`** (a holder of `access:grant:revoke` · the subject/self-revoke · a standing approver for its (role,asset)) **· deactivation** (revokes the user's active grants). Every revoke/expiry audits and **tears down the dependent live sessions**. Duration is clamped to `min(requested, policy.max_duration, MaxGrantTTL=8h)`, snapshotted at request time. | One primitive for every time-boxed elevation (SSH grant, future PG step-up); grants join authz without mutating admin config (`role_bindings` stay standing-only); grants≠governance prevents self-escalation loops; symmetric approve/revoke authority; expiry is correct even without the reaper (the `expires_at > now()` filter), so the reaper is a side-effects (audit + teardown) job. |

## Notable non-choices (deferred by design)

- **RDP, Kubernetes, MySQL/Mongo, HTTP/API proxying** — later sub-projects; the
  two-tier data plane is designed so each is an additive worker.
- **Inline DLP / command blocking** and **AI-agent/MCP governance** — differentiation
  bets deferred until the core is proven.
- **HA / multi-region** — out of MVP scope.
